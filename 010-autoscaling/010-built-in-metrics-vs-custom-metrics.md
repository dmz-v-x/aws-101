## Built-in Metrics vs Custom Metrics in AWS Auto Scaling — Understanding Metrics and Metric Granularity (1-Minute vs 5-Minute)

### 1. Introduction

Auto Scaling decisions depend on **metrics**. Metrics provide numerical measurements that describe how a system is performing over time.

Examples of metrics include:

```
CPU utilization
Network traffic
Request count
Memory usage
Queue length
```

These metrics help determine whether the infrastructure needs to:

```
Scale out → add more instances
Scale in → remove instances
```

In AWS Auto Scaling, metrics are collected and stored in **Amazon CloudWatch**.

There are two main types of metrics used in Auto Scaling:

```
Built-in metrics
Custom metrics
```

Another important concept is **metric granularity**, which determines how frequently metric data points are recorded.

Typical granularities include:

```
1-minute metrics
5-minute metrics
```

Understanding these concepts is critical because the accuracy and frequency of metrics directly affect how quickly Auto Scaling reacts to changes in workload.

---

### 2. What Are Metrics?

A **metric** is a time-based measurement representing the performance or behavior of a system.

Each metric consists of:

```
Metric name
Timestamp
Measured value
Dimensions (optional identifiers)
```

Example metric data:

```
Metric Name → CPUUtilization
Timestamp → 10:01 AM
Value → 72%
```

Metrics are collected periodically and stored in monitoring systems.

In AWS, the monitoring service responsible for metrics is:

```
Amazon CloudWatch
```

CloudWatch stores metrics and enables:

```
Monitoring dashboards
Alerting systems
Scaling decisions
Automated infrastructure management
```

---

### 3. Role of Metrics in Auto Scaling

Metrics act as the **input signals for scaling policies**.

Example scaling logic:

```
CPU utilization > 70%
↓
Scaling policy triggers
↓
Auto Scaling launches new instances
```

Without metrics, Auto Scaling cannot determine when infrastructure capacity needs to change.

Metrics allow the system to respond to:

```
Traffic spikes
Resource exhaustion
Application demand
Queue backlog
```

---

### 4. Built-in Metrics

Built-in metrics are metrics automatically generated by AWS services.

These metrics require **no additional configuration** and are available by default in CloudWatch.

They provide insights into infrastructure performance.

---

### 5. Common Built-in EC2 Metrics

Examples of built-in EC2 metrics include:

```
CPUUtilization
NetworkIn
NetworkOut
DiskReadOps
DiskWriteOps
DiskReadBytes
DiskWriteBytes
StatusCheckFailed
```

These metrics help monitor how EC2 instances are performing.

Example metric:

```
CPUUtilization = 80%
```

This may indicate that the instance is under heavy load.

---

### 6. Built-in Auto Scaling Metrics

Auto Scaling Groups also publish their own metrics.

Examples include:

```
GroupDesiredCapacity
GroupInServiceInstances
GroupPendingInstances
GroupTerminatingInstances
GroupTotalInstances
```

These metrics provide visibility into the state of the Auto Scaling Group.

Example:

```
GroupDesiredCapacity = 6
GroupInServiceInstances = 5
```

This indicates that one instance is still launching.

---

### 7. Advantages of Built-in Metrics

Built-in metrics offer several advantages.

---

#### No Configuration Required

They are automatically available once the service is running.

---

#### Reliable and Standardized

AWS collects and manages these metrics automatically.

---

#### Infrastructure Visibility

They provide insight into system-level performance.

---

### 8. Limitations of Built-in Metrics

Built-in metrics only provide **generic infrastructure-level information**.

They do not capture application-specific behavior.

Example scenario:

```
Application overloaded
But CPU utilization remains low
```

In this case:

```
Built-in metrics may not reflect the real problem
```

This is where **custom metrics** become useful.

---

### 9. Custom Metrics

Custom metrics are metrics created and published by users or applications.

They allow organizations to monitor **application-specific behavior** that built-in metrics cannot capture.

Applications can send custom metrics to CloudWatch using:

```
AWS SDK
CloudWatch API
Monitoring agents
```

Custom metrics enable Auto Scaling based on **business logic rather than infrastructure metrics**.

---

### 10. Examples of Custom Metrics

Examples of useful custom metrics include:

```
Requests per second
Active users
API latency
Queue length
Database connection count
Cache hit rate
Background job backlog
```

Example metric:

```
MessagesInQueue = 500
```

If the queue grows too large:

```
Auto Scaling launches more worker instances
```

---

### 11. Example Custom Metric Workflow

Example architecture:

```
Application processes messages from queue
↓
Queue length increases
↓
Application publishes metric to CloudWatch
↓
CloudWatch alarm triggers scaling policy
↓
Auto Scaling launches additional workers
```

This allows scaling to be driven by **real workload demand**.

---

### 12. Publishing Custom Metrics

Applications publish custom metrics using CloudWatch APIs.

Example data structure:

```
MetricName: RequestCount
Namespace: MyApplication
Value: 200
Timestamp: 10:05 AM
```

These metrics can then be used in:

```
CloudWatch dashboards
Scaling policies
Alerts
```

Custom metrics provide powerful control over scaling behavior.

---

### 13. Metric Granularity

Metric granularity refers to **how frequently metric data points are recorded**.

Common metric granularities include:

```
1-minute granularity
5-minute granularity
```

Granularity affects how quickly Auto Scaling can respond to workload changes.

---

### 14. 5-Minute Metrics

By default, many EC2 metrics are collected every **5 minutes**.

Example data points:

```
10:00 → CPU 40%
10:05 → CPU 75%
10:10 → CPU 50%
```

With this granularity, scaling decisions occur at longer intervals.

Advantages:

```
Lower monitoring overhead
Less metric storage cost
Suitable for stable workloads
```

Disadvantages:

```
Slow reaction to sudden traffic spikes
Delayed scaling response
```

---

### 15. 1-Minute Metrics (Detailed Monitoring)

AWS also supports **1-minute metric granularity** through detailed monitoring.

Example data points:

```
10:00 → CPU 40%
10:01 → CPU 55%
10:02 → CPU 75%
10:03 → CPU 82%
10:04 → CPU 78%
```

With more frequent data points, Auto Scaling can respond faster.

Advantages:

```
Faster scaling decisions
More accurate monitoring
Better detection of traffic spikes
```

Disadvantages:

```
Slightly higher monitoring cost
More data storage
```

---

### 16. Impact of Granularity on Auto Scaling

Metric granularity directly affects how quickly Auto Scaling responds.

Example scenario:

Traffic spike occurs at:

```
10:02
```

---

#### With 5-Minute Metrics

Next metric recorded at:

```
10:05
```

Scaling decision occurs later.

---

#### With 1-Minute Metrics

Next metric recorded at:

```
10:03
```

Scaling action occurs much sooner.

This difference can be critical for high-traffic applications.

---

### 17. Choosing the Right Metric Type

Different workloads benefit from different metrics.

---

#### Use Built-in Metrics When

```
Scaling based on CPU
Monitoring infrastructure performance
Running simple workloads
```

---

#### Use Custom Metrics When

```
Scaling based on application demand
Monitoring queue-based systems
Tracking API traffic
Measuring business-specific workloads
```

---

### 18. Real-World Example

Consider a video processing service.

Each server processes uploaded videos.

Relevant metric:

```
Videos waiting in queue
```

If queue length exceeds:

```
100 videos
```

Auto Scaling launches additional processing instances.

Example scaling flow:

```
User uploads video
↓
Queue size increases
↓
Custom metric updated
↓
CloudWatch alarm triggers
↓
Auto Scaling launches workers
```

---

### 19. Best Practices for Metrics in Auto Scaling

To design effective scaling policies, several best practices should be followed.

---

#### Choose Metrics That Represent Real Load

CPU may not always reflect application demand.

Queue length or request rate may be better indicators.

---

#### Use 1-Minute Granularity for Production Systems

Fast-growing systems benefit from quicker scaling responses.

---

#### Monitor Both Infrastructure and Application Metrics

Combine built-in and custom metrics for full visibility.

---

#### Avoid Overly Sensitive Metrics

Metrics that fluctuate rapidly may cause unnecessary scaling events.

---

### 20. Summary

Metrics are the foundation of Auto Scaling decisions.

AWS Auto Scaling uses metrics collected in **Amazon CloudWatch** to determine when infrastructure should scale.

Two types of metrics are commonly used:

```
Built-in metrics → provided automatically by AWS
Custom metrics → defined by applications
```

Metric granularity determines how frequently metrics are recorded.

Common options include:

```
5-minute metrics → slower response, lower overhead
1-minute metrics → faster response, more precise scaling
```
