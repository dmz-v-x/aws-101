## Service Roles Explained

In AWS, many services need permission to interact with **other AWS services**.

For example:

A compute instance may need to read files from storage.  
A serverless function may need to write logs.  
A container task may need to read secrets.

However, AWS services themselves **do not automatically have permission** to access other services.

AWS follows a strict security model where **every action must be authorized**.

This is where **service roles** come into play.

A service role is an IAM role that an AWS service assumes in order to perform actions on your behalf.

---

### 1. Why Services Need Permissions

AWS services often need to perform actions inside your account.

Examples include:

A Lambda function writing logs to CloudWatch.  
A compute instance reading files from storage.  
A container task pulling secrets from a secrets manager.  
A deployment service launching compute instances.

Even though these services are part of AWS, they **cannot access your resources unless explicitly permitted**.

This is because AWS enforces a strong principle:

Everything is denied unless explicitly allowed.

So when a service needs to perform actions, you must give it permissions through an **IAM role**.

---

### 2. What Is a Service Role

A **service role** is an IAM role that is assumed by an AWS service.

Instead of a human or application assuming the role, the **AWS service assumes it automatically**.

This allows the service to access resources using **temporary credentials generated by STS**.

Example structure:

    AWS Service
         ↓
    Assumes Service Role
         ↓
    Temporary Credentials
         ↓
    Access AWS Resources

This mechanism allows AWS services to perform actions securely without using permanent credentials.

---

### 3. Example — Lambda Service Role

Imagine a Lambda function that processes images stored in a storage bucket.

The function needs permission to:

Read objects from the bucket.  
Write logs to CloudWatch.

To enable this, a service role is created.

Example role permission policy:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": "s3:GetObject",
          "Resource": "arn:aws:s3:::image-bucket/*"
        },
        {
          "Effect": "Allow",
          "Action": [
            "logs:CreateLogGroup",
            "logs:CreateLogStream",
            "logs:PutLogEvents"
          ],
          "Resource": "*"
        }
      ]
    }

When the Lambda function runs:

Step 1  
Lambda assumes the role.

Step 2  
STS generates temporary credentials.

Step 3  
Lambda uses those credentials to read images and write logs.

---

### 4. Service Principal Concept

Every IAM role has a **trust policy** that defines who is allowed to assume the role.

For service roles, the trust policy specifies an **AWS service as the principal**.

This is called a **service principal**.

A service principal identifies the AWS service that is allowed to assume the role.

Example trust policy for Lambda:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": {
            "Service": "lambda.amazonaws.com"
          },
          "Action": "sts:AssumeRole"
        }
      ]
    }

Here:

Service → lambda.amazonaws.com

This means the Lambda service can assume the role.

---

### 5. Example Service Principals

Different AWS services have different service principals.

Examples include:

Compute instances

    ec2.amazonaws.com

Serverless functions

    lambda.amazonaws.com

Container orchestration tasks

    ecs-tasks.amazonaws.com

Deployment service

    codedeploy.amazonaws.com

Container service

    eks.amazonaws.com

These identifiers tell AWS **which service is trusted to assume the role**.

---

### 6. Example — EC2 Service Role

Suppose an application running on a compute instance needs to upload logs to storage.

Instead of embedding access keys, you attach an IAM role to the instance.

Example role policy:

    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::app-logs/*"
    }

Trust policy:

    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }

Now the compute service assumes the role automatically.

The application receives temporary credentials from AWS.

---

### 7. How Service Roles Work Internally

The process works like this.

Step 1  
The AWS service starts running a resource.

Example:

Lambda execution  
Compute instance startup  
Container task launch

Step 2  
The service requests to assume the IAM role.

Step 3  
AWS STS generates temporary credentials.

Step 4  
The service uses those credentials to perform actions.

Step 5  
Credentials expire automatically.

This eliminates the need for permanent credentials.

---

### 8. Why Service Roles Are Important

Service roles provide several security benefits.

They remove the need for access keys in applications.

They use temporary credentials generated by STS.

Permissions are controlled using IAM policies.

Access follows the least privilege principle.

They reduce the risk of credential leakage.

Because of these advantages, service roles are the **recommended way for AWS services to access resources**.

---

### 9. Mental Model

Think of a service role as a **permission badge for an AWS service**.

Without the badge, the service cannot access your resources.

With the badge, the service can perform only the actions defined in the role.

The badge is temporary and managed automatically by AWS.

---

### Key Takeaways

Service roles allow AWS services to access other AWS resources securely.

They are IAM roles assumed automatically by AWS services.

Permissions are defined using IAM policies attached to the role.

The trust policy specifies the service principal that can assume the role.

Service principals identify AWS services such as Lambda, EC2, or ECS.

Service roles use temporary credentials generated by STS.

They eliminate the need to store permanent access keys in applications.
