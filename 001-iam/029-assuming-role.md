## AssumeRole (Core Mechanism)

AssumeRole is one of the **core mechanisms in AWS IAM**.

It is the process by which an identity temporarily gains the permissions of an **IAM role**.

Instead of giving permanent permissions to users or applications, AWS allows them to **assume a role and receive temporary credentials**.

These credentials are generated by **AWS STS (Security Token Service)** and expire after a certain time.

AssumeRole is heavily used in:

- Cross-account access
- Applications running on EC2
- Lambda functions
- DevOps workflows
- Federated authentication systems

Understanding AssumeRole is essential because it explains **how temporary access works in AWS**.

---

### 1. What “Assuming a Role” Means

When an identity assumes a role, it temporarily **inherits the permissions defined in that role**.

The process looks like this:

Identity → Requests role access → AWS STS generates temporary credentials → Identity uses role permissions.

Example:

A developer normally has limited permissions.

For a specific task, the developer assumes an **AdminRole**.

During that session, the developer temporarily receives **admin permissions**.

After the session expires, those permissions disappear.

---

### 2. Who Can Assume a Role

Several types of identities can assume IAM roles.

Common examples include:

IAM users

IAM roles

AWS services

External identities (federated users)

Another AWS account

Examples:

A developer assumes an admin role.

An EC2 instance assumes a role to access S3.

A Lambda function assumes a role to access DynamoDB.

A CI/CD pipeline assumes a deployment role.

This flexibility makes IAM roles extremely powerful.

---

### 3. Trust Policy (Who Is Allowed to Assume the Role)

Every IAM role contains a **trust policy**.

The trust policy defines **who is allowed to assume the role**.

Without a trust policy, no identity can assume the role.

Example trust policy:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": {
            "AWS": "arn:aws:iam::123456789012:user/Developer"
          },
          "Action": "sts:AssumeRole"
        }
      ]
    }

Explanation:

Principal → identifies who can assume the role.

Action → allows the sts:AssumeRole operation.

This means the **Developer IAM user** can assume the role.

---

### 4. Trust Policy Example for AWS Services

Roles used by AWS services must trust those services.

Example: EC2 role trust policy.

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": {
            "Service": "ec2.amazonaws.com"
          },
          "Action": "sts:AssumeRole"
        }
      ]
    }

This allows **EC2 instances** to assume the role.

Without this trust relationship, the service cannot use the role.

---

### 5. Permission Policy (What the Role Can Do)

The role also contains **permission policies**.

These define **what actions are allowed once the role is assumed**.

Example permission policy:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": [
            "s3:GetObject",
            "s3:PutObject"
          ],
          "Resource": "arn:aws:s3:::app-data/*"
        }
      ]
    }

This means:

Any identity that assumes this role can read and upload files to the **app-data bucket**.

---

### 6. Trust Policy vs Permission Policy

Roles always contain two important policy types.

Trust policy

Defines who can assume the role.

Permission policy

Defines what the role can do.

Example mental structure:

    Role
     ├── Trust Policy (who can assume)
     └── Permission Policy (what the role can do)

Both must work together for access to succeed.

---

### 7. Role Session

When a role is assumed, AWS creates a **role session**.

A role session is a temporary period during which the identity uses the role's permissions.

The session includes:

Temporary Access Key  
Temporary Secret Key  
Session Token  
Expiration time

Example session duration:

15 minutes  
1 hour  
Several hours (depending on configuration)

Once the session expires, the credentials stop working.

To continue accessing resources, the role must be assumed again.

---

### 8. Example AssumeRole Flow

Step 1

A developer requests to assume a role.

Step 2

AWS checks the role's trust policy.

Step 3

If allowed, AWS STS generates temporary credentials.

Step 4

The developer uses these credentials to make API calls.

Step 5

Credentials expire after the session duration.

---

### 9. Example Real-World Scenario

A company has two AWS accounts.

Account A → development environment.

Account B → production environment.

Developers work in Account A.

To deploy infrastructure to production, they assume a role in Account B.

Example flow:

Developer logs in to Account A.

Developer assumes DeploymentRole in Account B.

STS issues temporary credentials.

Developer deploys infrastructure.

Credentials expire automatically.

This approach avoids creating permanent users in the production account.

---

### 10. Mental Model

Think of AssumeRole as **borrowing permissions temporarily**.

Instead of permanently granting admin access, AWS allows identities to temporarily borrow those permissions through a role.

Once the session ends, the permissions disappear.

This makes access control more secure and flexible.

---

### Key Takeaways

AssumeRole is the mechanism used to temporarily gain the permissions of an IAM role.

Identities such as users, services, or external systems can assume roles.

Roles contain a trust policy that defines who can assume the role.

Roles also contain permission policies that define what actions are allowed.

When a role is assumed, AWS STS creates a temporary role session with short-lived credentials.

AssumeRole enables secure access for applications, services, and cross-account workflows.
