## EC2 IAM Roles

Applications running on EC2 instances often need to interact with other AWS services such as:

S3  
DynamoDB  
SQS  
CloudWatch  
Secrets Manager  

A common mistake beginners make is embedding **AWS access keys directly in application code**.

Example (bad practice):

    ACCESS_KEY=AKIA123EXAMPLE
    SECRET_KEY=abc123secret

This is dangerous because if the server is compromised, attackers can steal these credentials.

AWS solves this problem using **EC2 IAM Roles**.

With IAM roles, applications running on EC2 instances receive **temporary credentials automatically**, without storing any access keys.

---

### 1. What an EC2 IAM Role Is

An **EC2 IAM role** is an IAM role attached to an EC2 instance that grants permissions to applications running on that instance.

Instead of storing credentials in the application, the instance **assumes the role automatically**.

The process looks like this:

    EC2 Instance
        ↓
    Assumes IAM Role
        ↓
    STS generates temporary credentials
        ↓
    Application uses credentials to access AWS services

These credentials are temporary and automatically rotated by AWS.

---

### 2. Example Use Case

Imagine an application running on an EC2 instance that needs to upload logs to an S3 bucket.

Instead of using access keys, the EC2 instance is given an IAM role.

Example role permission policy:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": "s3:PutObject",
          "Resource": "arn:aws:s3:::app-logs/*"
        }
      ]
    }

This allows the application to upload logs to the bucket.

The application can now call S3 APIs without storing credentials.

---

### 3. Instance Profiles

An **instance profile** is the mechanism AWS uses to attach an IAM role to an EC2 instance.

In simple terms:

An instance profile is a **container for an IAM role that EC2 can use**.

When you attach a role to an EC2 instance in the AWS console, AWS actually attaches the **instance profile**.

Structure:

    IAM Role
        ↓
    Instance Profile
        ↓
    EC2 Instance

Instance profiles are automatically created when you create an EC2 role through the console.

---

### 4. Example Instance Profile Workflow

Step 1  
Create an IAM role with required permissions.

Step 2  
AWS creates an instance profile associated with the role.

Step 3  
Attach the instance profile to the EC2 instance.

Step 4  
The EC2 instance automatically receives temporary credentials.

Applications running on the instance can now access AWS services.

---

### 5. Metadata Service (High Level)

The EC2 **Instance Metadata Service (IMDS)** is a special internal endpoint available only inside the EC2 instance.

Applications use this service to retrieve information about the instance, including:

Instance ID  
Region  
Security credentials for the IAM role

The metadata service is accessible through a special internal IP address:

    http://169.254.169.254

Applications can request credentials from this endpoint.

AWS automatically provides **temporary credentials associated with the IAM role**.

---

### 6. Example Metadata Credential Request

An application running inside the EC2 instance can request credentials like this:

    http://169.254.169.254/latest/meta-data/iam/security-credentials/

This returns the name of the IAM role attached to the instance.

Example:

    app-server-role

Then the application requests the credentials:

    http://169.254.169.254/latest/meta-data/iam/security-credentials/app-server-role

The response includes temporary credentials:

    AccessKeyId
    SecretAccessKey
    Token
    Expiration

These credentials are generated by **AWS STS**.

---

### 7. How Applications Automatically Use These Credentials

Most AWS SDKs automatically retrieve credentials from the metadata service.

Example using the AWS SDK for JavaScript:

    const s3 = new AWS.S3();
    await s3.putObject({
      Bucket: "app-logs",
      Key: "log.txt",
      Body: "log data"
    });

No access keys are required.

The SDK automatically:

1. Queries the metadata service
2. Retrieves temporary credentials
3. Uses them to sign API requests

This process is completely automatic.

---

### 8. Credential Rotation

Temporary credentials obtained through instance roles **automatically rotate**.

AWS periodically refreshes the credentials before they expire.

Applications do not need to manage credential rotation manually.

This provides several benefits:

Reduced credential exposure  
Automatic key rotation  
No secret storage in applications

---

### 9. Why EC2 Roles Are Safer Than Access Keys

Using EC2 roles provides several major security advantages.

No credentials stored in code.

Credentials are temporary and expire automatically.

Permissions are centrally managed in IAM.

Credential rotation is automatic.

If an instance is compromised, credentials expire quickly.

This is why AWS strongly recommends using **IAM roles instead of access keys for EC2 applications**.

---

### 10. Mental Model

Think of an EC2 IAM role as a **temporary permission badge for the server**.

The server does not store permanent keys.

Instead, it requests a temporary badge from AWS whenever it needs to access resources.

That badge expires automatically and is replaced with a new one.

---

### Key Takeaways

EC2 IAM roles allow applications running on EC2 instances to access AWS services securely.

Roles provide temporary credentials generated by AWS STS.

Instance profiles are the mechanism used to attach IAM roles to EC2 instances.

The EC2 metadata service provides temporary credentials to applications running on the instance.

AWS SDKs automatically retrieve these credentials from the metadata service.

Using IAM roles eliminates the need to store access keys in application code and improves security.
