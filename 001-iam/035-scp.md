## Service Control Policies (SCPs)

Service Control Policies (SCPs) are a powerful security feature used in **AWS Organizations** to control what actions are allowed across multiple AWS accounts.

Unlike IAM policies, which grant permissions to users or roles, SCPs define the **maximum permissions that accounts within an organization can have**.

In simple terms:

IAM policies → Grant permissions  
SCPs → Set the maximum allowed permissions

Even if an IAM policy allows an action, the action will fail if the SCP denies it.

SCPs are therefore used to enforce **organization-wide security guardrails**.

---

### 1. What AWS Organizations Is (Context for SCPs)

SCPs exist only within **AWS Organizations**.

AWS Organizations is a service that allows companies to manage **multiple AWS accounts under one organization**.

Typical organization structure:

    AWS Organization
        │
        ├── Management Account
        │
        ├── Dev Account
        ├── Staging Account
        ├── Production Account
        ├── Security Account
        └── Logging Account

The **management account** controls policies that apply to all member accounts.

SCPs are attached to:

The entire organization  
Organizational Units (OUs)  
Individual accounts

---

### 2. What an SCP Is

A Service Control Policy is a JSON policy that **limits the permissions available to accounts within an organization**.

SCPs do not grant permissions.

They only define the **maximum allowed actions**.

If an action is not allowed by the SCP, it cannot be performed even if IAM policies allow it.

Example idea:

    SCP allows → ec2:StartInstances

IAM policy allows → ec2:TerminateInstances

Result:

TerminateInstances fails because SCP does not allow it.

---

### 3. Why SCPs Exist

SCPs exist to enforce **organization-wide security restrictions**.

They help central security teams control what accounts are allowed to do.

Examples of security rules enforced by SCPs:

Prevent disabling CloudTrail.

Prevent deleting security logs.

Prevent creating resources in unauthorized regions.

Prevent deleting production databases.

Prevent modifying IAM security controls.

SCPs act as **guardrails for all accounts in the organization**.

---

### 4. How SCPs Work with IAM Policies

To understand SCPs, it's important to understand their relationship with IAM.

Both IAM policies and SCPs are evaluated together.

Access is allowed only if:

IAM policy allows the action  
AND  
SCP allows the action

If either denies the action, the request fails.

Evaluation logic:

    IAM Allow
    +
    SCP Allow
    =
    Request Allowed

But:

    IAM Allow
    +
    SCP Deny
    =
    Request Denied

---

### 5. Example SCP

Example SCP that blocks deleting S3 buckets.

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Deny",
          "Action": "s3:DeleteBucket",
          "Resource": "*"
        }
      ]
    }

If this SCP is applied:

No account in the organization can delete S3 buckets.

Even administrators cannot bypass it unless the SCP is modified.

---

### 6. SCP Attachment Levels

SCPs can be attached at different levels of the organization.

Organization Root

Applies to all accounts.

Organizational Unit (OU)

Applies to all accounts within that OU.

Individual Account

Applies only to that specific account.

Example structure:

    Organization Root
        │
        ├── OU: Development
        │       ├── Dev Account
        │       └── Test Account
        │
        └── OU: Production
                └── Prod Account

You could apply stricter SCPs to the **Production OU** than the Development OU.

---

### 7. Common SCP Use Cases

Organizations use SCPs to enforce security and governance rules.

Prevent disabling security services.

Example:

Block disabling CloudTrail logging.

Restrict AWS regions.

Example:

Allow resources only in specific regions.

Protect production resources.

Example:

Block deleting RDS databases.

Prevent IAM privilege escalation.

Example:

Block creating new IAM administrators.

These rules ensure accounts follow **company security policies**.

---

### 8. Example — Restrict AWS Regions

A company may want to allow resources only in approved regions.

Example SCP:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Deny",
          "NotAction": [
            "iam:*",
            "route53:*",
            "cloudfront:*"
          ],
          "Resource": "*",
          "Condition": {
            "StringNotEquals": {
              "aws:RequestedRegion": [
                "us-east-1",
                "us-west-2"
              ]
            }
          }
        }
      ]
    }

This policy blocks resource creation outside approved regions.

---

### 9. Example — Protect CloudTrail

Security teams often ensure CloudTrail cannot be disabled.

Example SCP:

    {
      "Effect": "Deny",
      "Action": [
        "cloudtrail:DeleteTrail",
        "cloudtrail:StopLogging"
      ],
      "Resource": "*"
    }

This ensures audit logging remains enabled.

---

### 10. SCP Allow List vs Deny List Strategy

There are two ways to design SCPs.

Allow-list strategy

Only explicitly allowed actions are permitted.

Everything else is blocked.

Deny-list strategy

Most actions are allowed.

Only specific dangerous actions are denied.

Most organizations use **deny-list SCPs** because they are easier to manage.

---

### 11. Important Limitations of SCPs

SCPs have several important limitations.

SCPs do not grant permissions.

They only restrict permissions.

SCPs do not apply to the management account.

The management account always retains full control.

SCPs affect IAM users, roles, and services within member accounts.

They do not replace IAM policies.

IAM policies are still required to grant access.

---

### 12. Debugging SCP Issues

Sometimes actions fail even though IAM policies allow them.

One common reason is an SCP restriction.

To debug SCP issues:

Check IAM policy permissions.

Check SCP policies applied to the account.

Check SCP policies applied to the OU.

Check organization-level SCPs.

AWS CloudTrail logs can help identify SCP-related access denials.

---

### 13. Real-World Enterprise Example

Large companies often enforce strict SCP rules.

Example organization policy:

Development accounts:

Allow most services.

Production accounts:

Restrict destructive actions.

Security accounts:

Allow only auditing services.

Example guardrails:

Prevent deleting CloudTrail logs.

Prevent disabling GuardDuty.

Prevent modifying IAM security roles.

This ensures all accounts follow **corporate security standards**.

---

### 14. Mental Model

Think of SCPs as **organization-wide guardrails**.

IAM policies decide what a user or role is allowed to do.

SCPs define the maximum actions that any account is allowed to perform.

Even administrators cannot perform actions outside SCP limits.

---

### Key Takeaways

Service Control Policies are used in AWS Organizations to control permissions across multiple accounts.

SCPs define the maximum allowed permissions for accounts.

They do not grant permissions — they only restrict them.

Both IAM policies and SCPs must allow an action for it to succeed.

SCPs are commonly used to enforce security guardrails such as preventing resource deletion, restricting regions, and protecting logging systems.

They are essential for managing security in large multi-account AWS environments.
