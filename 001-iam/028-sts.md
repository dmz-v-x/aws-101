## What is STS

AWS STS stands for **AWS Security Token Service**.

STS is the AWS service responsible for generating **temporary security credentials** that allow identities to access AWS resources for a limited time.

Instead of using long-term credentials like permanent access keys, STS provides **temporary credentials that automatically expire**.

These temporary credentials are widely used in modern AWS architectures because they significantly improve security.

STS is used whenever:

- IAM roles are assumed
- Cross-account access is performed
- Federated users log in
- AWS services access other AWS services
- Applications run on EC2, Lambda, or containers

In practice, **almost every role-based access mechanism in AWS depends on STS**.

---

### 1. Purpose of STS

The primary purpose of STS is to provide **temporary, short-lived credentials** that allow secure access to AWS resources.

Instead of giving permanent credentials to users or applications, STS issues credentials that:

- Expire automatically
- Have limited permissions
- Are valid only for a short session

This improves security by reducing the risks associated with long-term credentials.

The key benefits include:

Improved security  
Reduced credential exposure  
No need to store permanent secrets  
Safer application authentication  

STS therefore plays a central role in **modern AWS identity and access management**.

---

### 2. What STS Generates

When STS issues temporary credentials, it generates three pieces of information:

Access Key ID  
Secret Access Key  
Session Token  

Example response from STS:

    AccessKeyId: ASIAxxxxxxxxxxxx
    SecretAccessKey: abc123examplekey
    SessionToken: verylongsessiontoken
    Expiration: 2026-05-10T15:30:00Z

The session token is what makes the credentials temporary.

These credentials are then used to make AWS API requests until they expire.

---

### 3. Why STS Exists

Before role-based access was widely used, systems relied heavily on **long-term access keys**.

This caused several security problems:

Credentials stored in source code  
Credentials stored in configuration files  
Credentials leaked in repositories  
Credentials reused across systems  

STS solves this problem by allowing applications and users to receive **temporary credentials dynamically**.

Once the credentials expire, they become useless.

This dramatically reduces the risk of credential theft.

---

### 4. How IAM Roles Use STS

IAM roles do not have permanent credentials.

Instead, when an identity assumes a role, AWS uses STS to **generate temporary credentials for that role session**.

The process looks like this.

Step 1  
An identity requests to assume a role.

Step 2  
AWS verifies that the identity is allowed to assume the role.

Step 3  
STS generates temporary credentials.

Step 4  
The identity uses those credentials to access AWS services.

Step 5  
Credentials expire after the session duration.

This process is called **role assumption**.

---

### 5. Example Role Assumption Flow

Imagine a developer wants temporary administrator access.

Step 1  
Developer logs into AWS.

Step 2  
Developer assumes an AdminRole.

Step 3  
STS generates temporary admin credentials.

Step 4  
Developer performs administrative actions.

Step 5  
Credentials expire automatically.

After expiration, the developer no longer has administrative privileges.

---

### 6. Example STS CLI Request

Example command using AWS CLI to assume a role.

    aws sts assume-role \
        --role-arn arn:aws:iam::123456789012:role/AdminRole \
        --role-session-name DevSession

STS returns temporary credentials such as:

    AccessKeyId
    SecretAccessKey
    SessionToken
    Expiration

These credentials can then be used for API calls.

---

### 7. STS in AWS Services

Many AWS services automatically use STS behind the scenes.

Examples include:

EC2 instance roles

Lambda execution roles

ECS task roles

EKS service accounts

In these cases, AWS automatically requests temporary credentials from STS.

Applications running on these services receive credentials without storing access keys.

This eliminates the need to manage secrets manually.

---

### 8. STS and Cross-Account Access

STS is also used when accessing resources across AWS accounts.

Example scenario:

Account A has a developer.

Account B has production infrastructure.

Instead of creating duplicate users in Account B, the developer can assume a role in Account B.

STS issues temporary credentials that allow the developer to access Account B.

This enables secure **cross-account access**.

---

### 9. Mental Model

Think of STS as a **temporary credential generator**.

Instead of giving someone permanent access keys, STS issues a temporary access badge.

That badge works for a limited time and then automatically expires.

IAM roles rely on STS to create these temporary credentials whenever a role is assumed.

---

### Key Takeaways

AWS STS (Security Token Service) generates temporary credentials for accessing AWS resources.

Temporary credentials consist of an access key ID, secret access key, and session token.

STS improves security by eliminating the need for long-term credentials.

IAM roles rely on STS to generate temporary credentials whenever a role is assumed.

STS is widely used in applications, AWS services, federated access, and cross-account access.
