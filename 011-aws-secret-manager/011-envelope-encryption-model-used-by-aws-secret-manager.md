## Envelope Encryption Model Used by AWS Secrets Manager (Data Key vs CMK)

### 1. Introduction

AWS Secrets Manager stores **sensitive data** such as:

- Database passwords  
- API keys  
- OAuth tokens  
- Encryption secrets  

Because these values are highly sensitive, they must always be **encrypted at rest**.

AWS Secrets Manager uses a security architecture called **envelope encryption** to protect secret values.

Envelope encryption uses **two different types of keys**:

- **Customer Master Key (CMK)** — the master encryption key managed by AWS KMS  
- **Data Encryption Key (DEK)** — a temporary key used to encrypt the secret data  

This model provides **strong security, high performance, and scalability**.

---

### 2. The Problem With Encrypting Data Directly Using a Master Key

Suppose AWS Secrets Manager encrypted secrets **directly using a KMS master key**.

Example workflow:

    Secret → Encrypt with CMK → Store

This approach would cause several problems:

1. **Performance bottleneck**  
   Every encryption and decryption would require a call to AWS KMS.

2. **Scalability limitations**  
   Millions of secrets would generate heavy traffic to KMS.

3. **Higher costs**  
   KMS operations are billed per request.

4. **Increased latency**  
   Every read operation would require communication with KMS.

To solve this problem, AWS uses **envelope encryption**.

---

### 3. What is Envelope Encryption?

Envelope encryption is a layered encryption model.

Instead of encrypting the data directly with the master key, AWS uses:

- A **data key** to encrypt the data
- A **master key** to encrypt the data key

Conceptually:

    Secret Data
        |
        | encrypted using
        v
    Data Encryption Key (DEK)
        |
        | encrypted using
        v
    Customer Master Key (CMK)

The master key never encrypts the data directly.

Instead, it protects the **data encryption key**.

---

### 4. Components of Envelope Encryption

Envelope encryption uses two types of keys.

---

### 5. Customer Master Key (CMK)

The **Customer Master Key (CMK)** is a key stored and managed inside **AWS Key Management Service (KMS)**.

Characteristics of the CMK:

- Stored securely in **AWS Hardware Security Modules (HSMs)**
- Never leaves AWS KMS in plaintext
- Used only to encrypt or decrypt **data keys**
- Access controlled using **IAM policies and key policies**

CMKs can be:

- **AWS-managed keys**
- **Customer-managed keys**

Example CMK ARN:

    arn:aws:kms:us-east-1:123456789012:key/abcd1234-5678-90ab-cdef-1234567890ab

The CMK acts as the **root of trust** for the encryption system.

---

### 6. Data Encryption Key (DEK)

A **Data Encryption Key (DEK)** is a temporary symmetric key used to encrypt the actual secret data.

Characteristics of the DEK:

- Generated by AWS KMS
- Used locally by Secrets Manager
- Used to encrypt the secret value
- Stored only in encrypted form

The plaintext version of the DEK exists **only briefly in memory** during encryption or decryption.

---

### 7. Encryption Process in Secrets Manager

When a new secret is stored, AWS performs the following steps.

---

### Step 1 — Request Data Key From KMS

Secrets Manager requests a data key from AWS KMS.

Example internal API call:

    GenerateDataKey

AWS KMS generates:

- Plaintext Data Key
- Encrypted Data Key

Output example:

    Plaintext DEK
    Encrypted DEK (encrypted with CMK)

---

### Step 2 — Encrypt the Secret

Secrets Manager uses the **plaintext data key** to encrypt the secret value.

Example:

    Secret Value → Encrypt using DEK → Encrypted Secret

This encryption happens **inside the Secrets Manager service**.

---

### Step 3 — Store Encrypted Secret

Secrets Manager stores:

- Encrypted secret value
- Encrypted data key

Example stored structure:

    {
      EncryptedSecret,
      EncryptedDataKey
    }

The plaintext data key is **immediately removed from memory**.

---

### 8. Decryption Process

When an application retrieves a secret, the following steps occur.

---

### Step 1 — Retrieve Stored Data

Secrets Manager retrieves:

- Encrypted secret
- Encrypted data key

---

### Step 2 — Decrypt the Data Key

Secrets Manager sends the encrypted data key to AWS KMS.

Example API call:

    Decrypt

KMS decrypts the encrypted data key using the **CMK**.

Result:

    Plaintext Data Key

---

### Step 3 — Decrypt the Secret

Secrets Manager uses the plaintext data key to decrypt the secret.

Example:

    Encrypted Secret → Decrypt using DEK → Plaintext Secret

The plaintext data key is again **discarded from memory** after use.

---

### 9. Visualization of Envelope Encryption

Encryption process:

    Secret Value
         |
         | Encrypt using DEK
         v
    Encrypted Secret
         |
         | Store along with
         v
    Encrypted Data Key (protected by CMK)

Decryption process:

    Encrypted Secret
         |
         | Request KMS to decrypt DEK
         v
    Plaintext DEK
         |
         | Decrypt secret
         v
    Plaintext Secret

---

### 10. Why Envelope Encryption Is Secure

Envelope encryption provides multiple security benefits.

---

### Separation of Responsibilities

- **CMK protects the data key**
- **Data key protects the data**

This layered protection increases security.

---

### Master Key Protection

The CMK:

- Never leaves AWS KMS
- Is protected by HSMs
- Is governed by strict IAM policies

---

### Limited Exposure of Data Keys

Plaintext data keys exist only:

- In memory
- For a very short time

They are never stored in plaintext.

---

### 11. Performance Benefits

Envelope encryption improves performance significantly.

Benefits include:

- Reduced calls to AWS KMS
- Faster encryption operations
- Lower latency
- Lower KMS cost

Because large data is encrypted locally, AWS KMS handles only **small data key operations**.

---

### 12. Where Envelope Encryption is Used in AWS

Envelope encryption is used across many AWS services.

Examples include:

- AWS Secrets Manager
- Amazon S3 Server-Side Encryption
- Amazon EBS encryption
- Amazon RDS encryption
- AWS Systems Manager Parameter Store

This model is a **core encryption design pattern in AWS security architecture**.

---

### 13. Example Secrets Manager Encryption Architecture

A typical encryption architecture looks like this:

    Application
        |
        | Store Secret
        v
    AWS Secrets Manager
        |
        | Request Data Key
        v
    AWS KMS (CMK)
        |
        | Return encrypted + plaintext DEK
        v
    Secret encrypted using DEK
        |
        v
    Store encrypted secret + encrypted DEK

When retrieving:

    Encrypted Secret
        |
        v
    KMS decrypts DEK
        |
        v
    Secret decrypted

---

### 14. Best Practices

Follow these best practices when working with encryption in Secrets Manager.

#### Use Customer Managed KMS Keys

This allows stricter access control and auditing.

---

#### Restrict KMS Access

Limit which roles can use the CMK.

---

#### Enable Key Rotation

Rotate CMKs periodically for improved security.

---

#### Monitor KMS Usage

Use **AWS CloudTrail** to track encryption and decryption operations.

---

### 15. Summary

AWS Secrets Manager uses **envelope encryption** to securely store secret values.

The model uses two key types:

| Key Type | Purpose |
|------|------|
| Data Encryption Key (DEK) | Encrypts the secret value |
| Customer Master Key (CMK) | Encrypts the data key |

Encryption workflow:

1. KMS generates a data key  
2. Secret is encrypted using the data key  
3. Data key is encrypted using the CMK  
4. Both encrypted data and encrypted key are stored  

Decryption workflow:

1. KMS decrypts the data key  
2. Data key decrypts the secret  

This layered approach provides:

- Strong encryption security  
- Reduced latency  
- High scalability  
- Efficient use of AWS KMS
